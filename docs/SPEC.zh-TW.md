# Readback 規格（c0mpiled-18，2026-11-11）

題目：YC Fall 2026 Requests for Startups 的「Multiplayer AI」。

## 一句話

多人共用同一個 agent 工作階段時，每句話都看得到：agent 接住了嗎？之後還記得嗎？換模型接手後還在嗎？

## 要解決的問題

這些是使用者每天同時開十幾個 agent 對話時遇到的事：

1. 不確定 agent 有沒有完整理解輸入。
2. 不確定壓縮後 agent 還記不記得前面的重要內容。
3. 不知道何時該插話、何時該排隊。
4. 看不到每次送給模型的 prompt 和預計產出。
5. 想在不同廠商的模型之間交接，又怕品質掉。
6. 需要一張「等人回答」的清單。

## 誰在用

兩位隊友（Roy、Mia）各開一個瀏覽器視窗，對同一個 agent 說話。agent 把一件工作拆成幾步，一步一步做。

## 功能

### 1. 回條

- 訊息送出後立刻顯示「已送達」。
- 約 1–2 秒後，agent 回一張回條，有四欄：
  - 我聽到的是：agent 用自己的話複述。
  - 類型：新增、修改、撤回、回答、提問。
  - 何時生效：排隊或插話，附一句理由。
  - 預計產出。
- 排隊還是插話，由系統判斷：
  - 插話：繼續做下去會白做（正在用的事實、名字或方向被改正，或被叫停）。插話會中斷正在跑的那一步，丟掉寫到一半的內容，帶著更正重做。
  - 排隊：其他情況都排隊，到下一個檢查點才生效。拿不準就排隊。
- 排隊中的訊息，隊友可以按「立刻插話」或「取消」。
- 回條產生失敗時，訊息不會消失，會以原話排隊。

### 2. 檢查點

- 每一步開始前都有一個檢查點。
- 排隊的訊息在檢查點生效，交棒也在檢查點進行。
- 還有人沒回答必要的問題時，agent 停在檢查點等。
- 全部做完之後才送來的訊息，會自動多加一步來處理。

### 3. 記憶板

- 之後的步驟或接手的模型必須遵守的話，會自動釘上記憶板。
- 分三類：限制、決定、核准關卡。
- 釘的是隊友的原話，並記下是誰說的。
- 每一步的 prompt 最前面都原文帶入記憶板，不經過摘要。
- 被新訊息取代的條目不刪除，標成「已取代」。

### 4. 等你處理

- 排計畫時，如果缺具體資料（日期、價格、名字），agent 不亂編，改成提問，最多 2 題，並指定給某位隊友。
- 隊友說「要我看過才能完成」時，會產生一個核准關卡，指定給那位隊友。
- 回答之後，答案會釘成一條「決定」。

### 5. 交棒

- 按一下，把工作交給另一家的模型（Qwen、Gemini、DeepSeek、Grok）。
- 交接單由系統從現有狀態組出來，記憶板的原話原封不動帶過去。
- 每條釘選各有一題情境題。接手的模型逐題作答，由原本的模型評分。
- 沒答對的條目會再講一次、再考一次。
- 畫面逐條顯示結果，例如「接住 5/5」。

### 6. 看得到 prompt

- 每一步都能打開，看實際送給模型的完整 prompt。

## 畫面

- 上方是三條跑道：Roy、agent、Mia。
  - agent 跑道是步驟和檢查點。
  - 隊友說的話是圓點，用線連到 agent 接住它的地方。虛線是排隊中，實線是已生效。
- 下方三欄：訊息和回條、這一步的產出、記憶板加等你處理加交棒結果。

## 今晚不做

- 登入和權限。只有 Roy 和 Mia 兩個固定身分。
- 資料庫。工作階段存在記憶體，伺服器重啟就清空。
- 多人共同編輯同一段 prompt。
- 雲端部署。
- 真的把內容發布到外部平台。

## 技術

- 前端：Vite、React、TypeScript。
- 後端：一個 Node 行程，不用框架。狀態用 Server-Sent Events 推給所有視窗。
- 模型：GMI Cloud 的 API。
- 模型太快，一步只要幾秒，人來不及插話，所以有「放慢顯示」的開關。

## 驗收：90 秒 demo 要跑得出來

1. Roy 開一件工作，agent 列出 4 步並開始做。
2. 第 2 步進行中，Mia 說「100 字以內」。她拿到回條：排隊，下一個檢查點生效。這句話同時釘上記憶板。
3. Roy 更正一個正在用的事實。系統判斷要插話，那一步重做。
4. agent 缺發布日期，問題出現在 Roy 的「等你處理」。Roy 回答後繼續。
5. 按「交棒」換另一家的模型。考試結果逐條顯示，接手後的產出仍遵守記憶板。
